# M3 MCP Server and TypeScript SDK Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Expose the existing Inochi Agent Tools semantic authoring capabilities through a public TypeScript SDK and a stdio MCP server, with stable semantic schemas and real-artifact parity evidence against the CLI.

**Architecture:** `packages/sdk` is a thin public TypeScript facade over `@inochi-agent-tools/core`; it groups existing semantic functions without introducing authoring behavior. `packages/mcp` is a stdio MCP adapter over that SDK, using semantic tool names and JSON-schema validation. CLI, SDK, and MCP remain peers over the same semantic authority; no MCP/SDK code calls the D ABI or native host directly.

**Tech Stack:** Node.js >=22, TypeScript 5.9, Vitest 3.2, npm workspaces, `@modelcontextprotocol/server@2.0.0`, pinned Inochi2D `fdb241da048dbe330152f7b0015e2129dc392844` (`v0.8.7`), existing native/Creator acceptance harness.

**Spec:** `docs/superpowers/specs/2026-09-13-inochi-agent-tools-v1-design.md`

## Global Constraints

- Public/general-purpose only: no Away Message names, gameplay assumptions, or character-specific API.
- Inochi2D authority remains exact commit `fdb241da048dbe330152f7b0015e2129dc392844` on `v0_8`, declaring `IN_VERSION = "v0.8.7"`.
- LDC remains >= 1.40.0.
- `@inochi-agent-tools/core` remains the sole semantic authoring authority.
- MCP and SDK must not expose raw `in_*`, allocators, pointers, memory offsets, or implementation-specific native handles.
- Runtime and authoring remain separable.
- Real `.inp` and real PNG artifacts are mandatory for integration/acceptance proof.
- Existing M2 Creator and M3 CLI gates must remain green; no reduced acceptance path is allowed.
- v1 transport scope is stdio MCP only. Streamable HTTP, auth, remote deployment, resources/prompts, Creator UI, automatic rigging, and application adapters are out of scope.
- Strict RED -> GREEN for every behavioral slice.

**Files:**
- Create: `packages/mcp/package.json`

- Modify: `package.json`
- Modify: `package-lock.json`

**Interfaces:**
- Consumes: `createAuthoringClient(): AuthoringClient`.
- Produces these v1 MCP tools:
  - `puppet.create`
  - `puppet.open`
  - `puppet.inspect`
  - `puppet.validate`
  - `puppet.save`
  - `puppet.edit`
  - `parameter.evaluate`

`puppet.open` and `puppet.inspect` may delegate to the same semantic inspection primitive, matching the established CLI contract. `puppet.edit` accepts the existing semantic edit-operation array, so texture import, hierarchy/Part creation, parameter creation, binding, and related v1 edit operations remain core-defined rather than duplicated as MCP behavior.

Each successful tool result must expose a stable structured content payload:

```ts
{ ok: true, result: semanticResult }
```

Each semantic failure must map to:

```ts
{ ok: false, error: { code: semanticCode, message, details? } }
```

No stack traces or native implementation details in normal tool results.
